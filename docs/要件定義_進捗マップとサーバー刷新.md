| FR-5 オフラインの線引き | **実装済み** | 実績入力はオフラインのまま。進捗マップだけオンライン |

**7章の設計から1点変えた。** `pull` が返す `works` を、アプリは使わない。
サーバーの「作業」シートには進捗マップに要る要約（状態・実績量・記録者）しか
置いていないため、薬剤の明細を含む作業の完全な内容までは復元できない。
そのため役割を次のように分けた。

- **進捗（works）は送るだけの片方向。** 他の端末の作業内容は取り込まない
- **圃場（fields）は双方向。** ポリゴンを含む完全な内容をサーバーに置ける
- 作業の完全な内容の共有が要るなら、従来の `cloudSave` / `cloudLoad` が担う（当面残す）

`pull` の `works` はサーバー側に実装済みで、テストもある。将来アプリ側で
使うときのために残してあるだけで、現在アプリは呼んでいない。

### 検証

```
node tools/selftest.cjs   # 107件（計算・同期の時刻打ち・進捗の状態順序）
node tools/gastest.cjs    # 50件（受信処理・競合・権限・数式インジェクション）
```

加えて、ローカルに立てた受信口（`tools/fakegas.cjs`）に対して
ブラウザから実際に送信し、次を確認した。

1. 圃場3件・作業2件が「圃場マスタ」「作業」シートに1件1行で入る
2. **作業を1件も持たない別端末が、サーバー経由で他端末の実績を地図に表示する**
   （北の田=実績済/緑、南の田=調合済/黄、東の田=対象外/灰）
3. 未送信の実績は橙で出て、集計バーに「未送信 1」と出る

なお `index.html` の CSP（`connect-src`）が送信先を Apps Script に限っているため、
この確認は CSP を緩めた一時コピーで行った。**リポジトリの CSP は変えていない。**

## 1. 現状（コードで確認済み）

| 層 | 実体 | 根拠 |
|---|---|---|
| 画面 | React UMD 同梱 + Leaflet / Google Maps。`app.js` 単一ファイル 8,845行 | `app.js:1-8845` |
| 端末保存 | localStorage（`tankmix:fields` / `works` / `chemMaster` / `presets` / `crops`）、農薬DBのみ IndexedDB | `app.js:443-455` |
| 配信 | GitHub Pages（**PUBLIC**）+ Service Worker 全ファイルキャッシュ | `sw.js:3-17` |
| サーバー | Google Apps Script ウェブアプリ（アクセス: 全員）+ スプレッドシート | `Code.gs` |
| 認証 | チーム共通の合言葉 1つ（`SHARED_SECRET`）。記録者名は自己申告 | `Code.gs:sharedSecret_` |
| 地図 | 既定 Leaflet。Google Maps は各端末が自分のAPIキーを入れたときのみ | `app.js:573,5134` |

GAS が受ける4種のリクエスト:

- `type=record` / `report` … 「防除記録」シートに 1散布=1行 で追記・更新
- `type=cloudSave` / `cloudLoad` … 「_共有データ」シートに **1チーム=1セル** でJSON全体を保存／読込
- `type=chemdbLoad` … Drive上の `chemdb.json` を25万文字ずつ分割配信

作業（work）が持つ進捗状態: `reported` / `synced` / `reportSynced`（`app.js:763-783`）。
画面上は「計画 / 調合済 / 実績入力済(未送信) / ✓送信済」の4段階（`app.js:3114-3115`）。

## 2. 現状のままでは進捗マップが成立しない理由

要望「実績入力を終えた圃場の色が変わる進捗マップ」は、**他人の進捗が自分の端末に届くこと**が前提。
現行はそこが成立していない。

1. **共有が全置換（last-write-wins）**
   `cloudSave` は 1チーム1セルを丸ごと差し替える（`Code.gs` cloudSave、`app.js:1346-1386`）。
   Aさんが保存した瞬間、Bさんが入れた実績は消える。`_共有データ履歴` シートは
   「消えることを前提に手動で戻す」ための仕組みで、同時作業には耐えない。

2. **45,000文字の上限が既に効いている**
   `fields`（ポリゴン座標）+ `works` + `chemMaster` + `presets` を1セルに詰めるため、
   圃場が増えると保存不能になる。v8.49 でこの上限を踏んで修正済み。

3. **記録シートから地図を描き戻せない**
   「防除記録」シートは圃場を**名前の文字列**でしか持たない（`Code.gs` HEADERS 5列目）。
   `fieldId` も座標もないので、シート側の実績と地図上のポリゴンを結び付けられない。

4. **誰の実績か保証がない**
   認証はチーム共通の合言葉のみ。

→ **結論：進捗マップは画面の追加では作れない。「1圃場1行 / 1作業1行」の差分更新モデルへの
サーバー刷新が前提条件。** これが今回の改修の本体。

### 「チーム」の単位についての解釈（重要）

Q1「2班で散布することがある」に対し、次の解釈で設計する。**違っていれば指摘してほしい。**

- **チームコード = 会社（圃場群）の単位。** 2班が同時に散布する場合も**同じチームコード**を使う
- 班の区別は**記録者名**で行う
- 理由：別々のチームコードにすると相互のデータが見えず、進捗マップの目的
  （「もう一方の班がどこまで終わったか」を見る）が達成できないため
- 他社に配る分だけが別チーム＝別スプレッドシート

## 4. 機能要件

### FR-1 進捗マップ（新タブ）

既存の圃場マップ（作図・編集用）とは**別タブ**。進捗マップに編集操作は置かない
（誤操作でポリゴンを壊す事故を防ぐ）。

- **表示対象期間**：既定＝選択中の作業日。切替として「当日／期間指定／シーズン累計」
- **色分け**（Q4により4段階に簡素化）

  | 状態 | 色 | 判定 |
  |---|---|---|
  | 対象外（その日の作業リストに無い） | 灰・細枠 | 該当 work なし |
  | 未実績 | 白地・赤枠（現行色を踏襲） | `status = planned` |
  | 実績済（自分の端末で入力・未送信） | 橙 | 端末ローカルの `reported && !reportSynced` |
  | 実績済（サーバー確定） | 緑 | `status = done` |

- **凡例**を常時表示。色だけに頼らず、圃場ラベルに状態記号（✓）も併記する
  （屋外・直射日光下の視認性、および色覚特性への配慮）
- 圃場タップ → 圃場名・作業内容・実績量・**入力者**・入力時刻
- 上部の集計バー：`実績 n / m 圃場` `実績面積 xx a` `未実績 n`
- **更新**：手動の「🔄 最新を取得」ボタンのみ（Q5）。
  取得したスナップショットを端末に保持し、画面に `最終取得 HH:MM` を常時表示する。
  圏外では取得できないため、その旨を明示する

### FR-2 メンバーの現在地表示（任意機能・既定OFF）

Q4「可能なら位置情報のみ分かれば助かる」への対応。**位置情報は個人情報のため、別要件として扱う。**

- **既定OFF。** 設定タブで端末ごとに明示的にONにしたときだけ送信する
- ONにする画面で、送信内容を明示する：
  「記録者名・緯度経度・送信時刻を、チームのスプレッドシートに送ります。
  　同じチームコードの端末から見えます。ONの間だけ送信します」
- 送信タイミング：**進捗マップを開いている間に、手動更新ボタンを押したときのみ**
  （バックグラウンド常時送信はしない。電池と通信量、および追跡感を避けるため）
- サーバー側は**最新1件のみ保持し上書き**。移動履歴を残さない
- 一定時間（既定30分）更新のない端末は地図に出さない
- OFFにすると、サーバー上の自分の行を削除する

### FR-3 圃場・作業の共同編集で他人のデータを壊さない

- 保存単位を「圃場1件」「作業1件」に分割。**全置換API（cloudSave）は新規保存を停止**
- 同一レコードの競合は「`updatedAt` の新しい方を採用」＋**上書き前の値を履歴シートに残す**
- 削除は論理削除（`deletedAt`）。物理削除しない
  → 端末Aの削除が端末Bに伝わらず復活する事故を防ぐ

### FR-4 認証・権限

- **チーム合言葉（`SHARED_SECRET`）は維持。** 現場の再設定コストが低く、規模に見合う
- 端末に `deviceId`（初回起動時に生成するランダム文字列）を持たせ、全リクエストに乗せる。
  「誰が入力したか」を自己申告の記録者名だけに頼らない
- **他社への配布は、別スプレッドシート＋別GASデプロイ＋別合言葉。**
  同一デプロイでチームコードだけ分けると、認可の実装ミスが即データ漏れになる。
  シートを分ければその余地が構造的に無くなる
- **公開リポジトリ制約**：`https://fujimito.github.io/AGRI.APP.F/` は全世界から取得できる。
  GASのURLも合言葉も**アプリに埋め込まない**（現状どおり各端末で設定タブに入力）

### FR-5 オフラインの適用範囲（PWA方針）

「PWAにこだわらない」との指示だが、**全面オンライン化は推奨しない。**
実績入力が発生するのは圃場＝電波の不安定な場所であり、ここをオンライン必須にすると
入力そのものが落ちる。

| 機能 | オフライン |
|---|---|
| 調合計算・実績入力・記録閲覧 | **必須**（現状維持。SW とキュー送信を残す） |
| 圃場マップ（自分の圃場の表示） | 端末キャッシュで可 |
| **進捗マップ（チーム全体）** | **オンライン時のみ更新**。圏外は最終取得時刻つきスナップショット |
| 圃場・薬剤マスタの編集 | オフライン編集可、復帰時に差分同期 |

## 5. Q3への回答：有料サービスは不要

**案A（GAS継続）なら追加の月額費用はゼロ。** 根拠：

- Apps Script ウェブアプリ・スプレッドシート・Google Drive は、いま使っている
  Googleアカウントの範囲内。新しい契約は発生しない
- Q5（手動更新のみ）により、通信は「人がボタンを押した回数」だけ。
  自動ポーリングを入れないので、実行回数が想定外に膨らむ経路がない
- Q1（同時に数端末）により、`LockService` による直列化がボトルネックになる規模ではない

**ただし2点の但し書き（どちらも今回の改修とは別の既存事情）**

1. **Google Maps を選んだ端末は Maps Platform の課金対象。**
   既定は Leaflet で0円（`app.js:573`）。Googleマップは各端末が自分のAPIキーを
   入れたときだけ動く（`app.js:5134`）ので、その端末の持ち主に課金される
2. **GASのクォータ上限値は未確認。** 無料Gmailアカウントと Google Workspace
   （`@jupiter-ariake.com`）とで上限が異なる。実運用の規模では問題にならない見込みだが、
   数値としては未確認であり、断定しない

**Supabase 等の外部サービスが要るのは、次のいずれかに当たったとき**（今回は当たらない）:
自動更新（リアルタイム）が要る／同時書き込みが常時10端末を超える／
チームが増えてスプレッドシートを個別に配るのが管理しきれなくなる。

## 6. データモデル（新規シート）

### 6-1. `防除記録`（既存・変更しない）

Q6により現状維持。`type=record` / `type=report` の処理も現状のまま。
アグリノート転記とCSV出力の互換を壊さない。

### 6-2. `圃場マスタ`（新規・1圃場1行）

| 列 | 内容 |
|---|---|
| 圃場ID | `app.js` の `newId()` が返す数値。端末間で一意 |
| 名称 / 作物 / 地区 / 面積a | 圃場マスタの内容 |
| ポリゴン | 座標配列のJSON。丸め済み（`compactField`、`app.js:297`） |
| 中心lat / 中心lng | 進捗マップのラベル位置に使う |
| 更新日時 | ISO文字列。差分取得の基準 |
| 更新者 / 更新端末 | 記録者名と `deviceId` |
| 削除 | 論理削除フラグ |

1セル50,000文字の上限は**1圃場ぶんのポリゴンにしか掛からない**ため、実質的に消える
（頂点100点でも数KB）。これが現行45,000文字問題の解消そのもの。

### 6-3. `作業`（新規・1作業1行）

| 列 | 内容 |
|---|---|
| 作業ID / チームコード / 作業日 / 圃場ID | キー |
| 状態 | `planned` / `mixed` / `done` |
| 予定L / 実績L / 実績面積a / 薬剤内容 | 作業の中身 |
| 記録者 / 更新端末 / 実績入力日時 | 誰がいつ入れたか |
| 更新日時 / 削除 | 差分取得と論理削除 |

**進捗マップが読むのはこのシートだけ。**

### 6-4. `_共有データ履歴`（既存を流用・粒度を変更）

上書き前の値を1行ずつ積む。粒度を「チーム全体のJSON」から「レコード1件」に変更する。

### 6-5. `メンバー現在地`（新規・FR-2 が有効なときのみ）

| 列 | 内容 |
|---|---|
| 更新端末 / 記録者 / lat / lng / 更新日時 |

**端末ごとに1行。上書きのみ。履歴を残さない。**

## 7. API仕様（`doPost` の `type`）

全リクエストに `auth`（合言葉）と `deviceId` を乗せる。既存の照合処理をそのまま使う。

### 既存（変更しない）
`record` / `report` / `chemdbLoad`

### 既存（互換のため残すが、新規保存は停止）
`cloudSave` … 呼び出し側を段階的に `pushFields` / `pushWorks` へ置き換える
`cloudLoad` … 移行期間のみ。旧版の端末が残っている間の読み出し用

### 新規

| type | 引数 | 返り値 | 用途 |
|---|---|---|---|
| `progress` | `team`, `date`（または期間） | `[{fieldId, status, by, at, sprayedL}]` + `serverTime` | **進捗マップ専用。ポリゴンを返さない軽量応答** |
| `pull` | `team`, `since` | `{fields:[…], works:[…], serverTime}` | `since` 以降に更新された行だけ返す差分取得 |
| `pushFields` | `team`, `fields:[…]` | 件数 | 圃場のupsert（`updatedAt` 比較、上書き前を履歴へ） |
| `pushWorks` | `team`, `works:[…]` | 件数 | 作業のupsert（同上） |
| `ping` | `team`, `deviceId`, `lat`, `lng` | `[{by, lat, lng, at}]` | FR-2。**自分の位置を上書きし、他端末の最新位置を返す** |

`progress` がポリゴンを返さない点が要。ポリゴンは端末が既に持っており、
進捗マップは「圃場IDごとの色」だけ分かればよい。応答が小さいほど圏外近くでも通る。

## 8. 実装の順序

各段で単独で動く状態にする。途中で止めても現場が壊れないこと。

1. **GAS側に新シートとAPIを追加する。** 既存の record/report/cloudSave は一切触らない
   → この時点でアプリ側は無変更。既存運用に影響ゼロ
2. **アプリ側に `pushFields` / `pushWorks` / `pull` を実装。** cloudSave/cloudLoad と併存させ、
   設定タブから新方式を選べるようにする
3. **進捗マップタブを読み取り専用で追加**（`progress` を叩いて色を塗るだけ）
4. 実運用で1シーズン、または一定期間の並行稼働で検証
5. **cloudSave/cloudLoad の呼び出しを撤去**（GAS側の受け口は当面残す）
6. **FR-2（現在地）を追加。** ここだけ独立しているので最後でよい

各段の完了時に `node tools/selftest.cjs` が全項目成功すること、`sw.js` の
`CACHE_VERSION` を上げること（README「更新のしかた」）。
