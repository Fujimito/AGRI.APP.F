# 防除記録シートを転記元にできる状態にする 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 「防除記録」シートを**そのまま見てアグリノートへ転記できる1枚**にする。1つの散布作業が1行で、同じ圃場・同じ日が2行にならず、薬剤と実散布量が入っている状態を保つ。

**Architecture:** 台帳(防除記録)は「作業シートから作り直せる写し」として扱う(v9.07 の `ledgerRebuild_` で実証済み。実データで一致144・食い違い0)。これまで「元帳だから行を消さない(S3)」としていた方針を、**手動操作のときだけ・退避してから消せる**に緩める。重複行の発生源は圃場の二重登録なので、圃場側で検出して統合し、台帳は作り直しで整える。

**Tech Stack:** React 18(CDN・JSXなし。`React.createElement` を機械整形した形)／Google Apps Script／localStorage／`tools/selftest.cjs`・`tools/gastest.cjs`(Node の `vm` で読み込む自作ハーネス)

**Spec:** このファイルが spec を兼ねる。矛盾はここで解く。

## 背景(実測で確かめた事実)

2026-09-09〜09-12 の調査で、転記の邪魔をしているものが4つに割れた。

1. **予定だけの作業が台帳に書かれていた** … 圃場を予定へ入れた1.5秒後に自動送信され、薬剤も実績も無い行が台帳に載る。撒かずに翌日へ引き継ぐとその行は永久に凍る。実データで 2026-09-06 の34行がこの形。**v9.25 (`ledgerWorthy_`) で発生源は塞いだ。既存の凍った行は残っている。**
2. **凍った行を片付ける手段が無い** … 作り直しの下見で「台帳にしか無い(触らない) 657件」。
3. **同じ田んぼが端末ごとに別圃場として登録される** … 圃場IDは端末ごとの採番(`uid()`)。作業IDは「日付＋圃場ID」なので、別圃場なら別作業・別行になる。台帳の照合で「記録IDが重なっている行 0件」＝**同一IDの二重書き込みではなく、別IDの別行**。これが重複の本体。
4. **未送信件数の表示が実体と食い違う** … `pendingCount` は `isPending` だけを見ており、予定薬液量の一括計算のように `updatedAt` だけ動く変更を数えない。実測で「☁ 送信するものはありません」と出ている状態のボタンを押したら2件送られた。

## Spec(拘束力のある要求)

- **S1. 自動では1行も消さない。** 台帳の行を消すのは、人が設定タブで「作り直す」を押したときだけ。`pushWorks` を受けた側(`ledgerSyncWorks_`)は今までどおり足すか直すかしかしない。
- **S2. 消す前に必ず退避する。** 削除を伴う作り直しは、実行の最初に「防除記録」シートを丸ごと複製し、`防除記録_旧_YYYYMMDD_HHmm` を作ってから書き換える。複製に失敗したら**1行も触らずに中止**する。
- **S3. 他チームの行に触らない。** 消す対象はチームコードが一致する行だけ。**チーム欄が空の古い行は消さない**(どのチームのものか分からないため。`ledgerSyncWorks_` の拾い上げとは扱いを変える。拾うのは安全側だが、消すのは安全側ではない)。
- **S4. 消す件数を先に見せる。** 下見(dryRun)に「消す ◯件」を出し、実行のボタンにも件数を出す。確認ダイアログに**退避先のシート名**を出す。
- **S5. 統合は取り消せる前提で作らない。** 圃場の統合は共有データを書き換え、他の端末にも及ぶ。実行前に「残す圃場・消す圃場・付け替える作業の件数」を一覧で見せ、確認を取る。
- **S6. 統合で作業を失わない。** 付け替えた結果として作業IDが衝突する場合(勝ち圃場に同じ日の作業が既にある)、**実績のあるほうを必ず残す**。両方に実績があるときは統合せず、その組を「手で確認」として残す。
- **S7. 重複の判定は提案に留める。** 自動では統合しない。判定はあくまで「疑い」として出し、どれを残すかは人が決める。

## Task 1: 台帳の作り直しで、余分な行を退避してから消す

**版数: v9.27**／触る: `Code.gs` `app.js` `sw.js` `tools/gastest.cjs`

いまの `ledgerRebuild_(team, dryRun)` は「足す/直す/そのまま/台帳にしか無い(触らない)」を返す。この4つ目を消せるようにする。

- [ ] `ledgerRebuild_` に第3引数 `purge`(既定 false)を足す。`purge` が false のときの振る舞いは1行も変えない
- [ ] `purge` が true のとき、**最初に**「防除記録」シートを `copyTo` で複製し、`防除記録_旧_YYYYMMDD_HHmm` に改名する(S2)。複製が例外を投げたら、行は1つも触らずに `{ok:false, error:"backup"}` を返す
- [ ] 消す対象は「作業シートから作り直した行に無い記録ID」かつ「チームコードが引数の team と一致する行」だけ(S3)。チーム欄が空の行は数にも入れない
- [ ] 下見(dryRun)の戻り値に `purgeable`(消せる件数)と `backupName`(付ける予定のシート名)を足す
- [ ] `deleteRows` は下から上へ。上から消すと行番号がずれる
- [ ] アプリ側: 下見の表示に「消す ◯件」を足し、実行ボタンの文言を「下見のとおりに作り直す(足す◯/直す◯/消す◯)」にする。確認ダイアログに退避先シート名を出す(S4)

**受け入れ条件**

1. `purge:false` では既存の `gastest` が1件も落ちない
2. `purge:true` で、作業シートに無い・チーム一致の行だけが消える
3. チーム欄が空の行と、他チームの行は消えない
4. 複製に失敗したとき、台帳の行数が1行も変わらない
5. 消したあとにもう一度 `ledgerCheck` を通すと「作業に無い(台帳にはある)」が0件になる

**検証:** `node tools/gastest.cjs` と `node tools/selftest.cjs` が全件成功

## Task 2: 圃場の重複を「疑い」として出す

**版数: v9.28**／触る: `app.js` `sw.js` `tools/selftest.cjs`

- [ ] トップレベルに純関数 `duplicateFieldGroups(fields)` を足し、`EXPORTS` に加える
- [ ] 判定は2つ。どちらかに当たれば同じ組にする
  - **名前が一致** … `normalizeFieldName`(新設)で、前後の空白・全角半角・丸数字以外の記号の違いを吸収してから比べる
  - **場所が近い** … 両方にポリゴンがあり、重心どうしの距離が30m以内、かつ面積の差が20%以内。**30mと20%は暫定値(未計測)。** 実データで組数を見てから決め直す
- [ ] 1圃場が複数の組に入らないようにする(先に決まった組が勝つ)
- [ ] 圃場一覧の見出しに「⚠ 重複の疑い ◯組」を出す。押すと組ごとに並べ、各圃場の「面積・作業の件数・位置の有無・最後に触った日」を出す

**受け入れ条件**

1. 同名の2圃場が1組になる
2. 名前が違っても重心が近く面積も近ければ1組になる
3. 名前が同じでも、離れていて面積も違えば…**名前一致を優先して1組にする**(現場では同じ田んぼを別の位置で囲み直していることがあるため)
4. 圃場が1つ、または重複が無ければ0組。空配列でも落ちない
5. 1圃場が2つの組に現れない

**検証:** `node tools/selftest.cjs` が全件成功。判定関数を壊すと落ちることを確認する

## Task 3: 重複した圃場を統合する

**版数: v9.29**／触る: `app.js` `sw.js` `tools/selftest.cjs`

**ここが一番危ない。** 共有データを書き換え、他の端末にも及ぶ。純関数とUIを分け、純関数を先に固める。

- [ ] トップレベルに純関数 `mergeFieldsPlan(works, keepId, dropIds)` を足す。**計画を返すだけで、何も書き換えない**
  - 返すもの: `move`(付け替える作業の新旧ID)・`drop`(墓標を積む作業ID)・`conflict`(統合できない組)
  - 付け替え先の作業IDは `workIdFor(日付, keepId, nth, device)` で作り直す。**IDが変わるので、古いIDには墓標を積む**
  - 勝ち圃場に同じ日の作業が既にあるとき: 実績のあるほうを残す(S6)。両方に実績があれば `conflict` に入れて統合しない
- [ ] UI: 組ごとに「残す圃場」を選ばせる。既定の推奨は「位置が登録されていて、作業の件数が多いほう」
- [ ] 実行前に「残す/消す/付け替える作業◯件/統合できない◯件」を確認ダイアログに出す(S5)
- [ ] 実行: 作業の付け替え → 古い作業に墓標 → 負け圃場に墓標 → `pushProgress` と `pushFieldsSync` で送る
- [ ] 実行後に「台帳の作り直し(下見)」へ誘導する。台帳の古い行は Task 1 の削除で片付く

**受け入れ条件**

1. 付け替えた作業の圃場IDが勝ちIDになり、作業IDも新しいIDになる
2. 古い作業IDに墓標が積まれる(積まないとサーバーに残って二重になる)
3. 同じ日に両方の圃場の作業があり、片方だけ実績があるとき、実績のあるほうが残る
4. 両方に実績があるときは統合せず `conflict` に入る
5. 統合しても過去の作業の表示が壊れない(作業は `snapshot` を持っている)

**検証:** `node tools/selftest.cjs` が全件成功。3と4は表を作って1件ずつ確かめる

## やらないこと

- **送信を当日分に絞る。** 圏外だった過去日の記録が送られなくなる。日付が混ざって見えるのは台帳の並び順の問題なので、必要なら並び替えで解く
- **圃場IDの採番規則を変える。** 既存データのIDが変わり、過去の作業と台帳の結び付きが切れる
- **`ledgerSyncWorks_` に削除を足す。** 送信のたびに行が消える経路を作らない(S1)
