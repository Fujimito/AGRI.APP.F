01全体像

app.js は React.createElement に展開済みのプレーンJS。ブラウザがそのまま読む。

端末はそれぞれが完全な記録を持つ。サーバーは同期の待ち合わせ場所であって、正本ではない。圏外で1日中作業しても、端末だけで予定・計算・実績入力が完結する。

常時接続は持たない

WebSocket も常駐ポーリングもない。送るときだけ HTTPS で1往復する。アプリを閉じている間は同期が動かないだけで、次に開けば未送信ぶんから再開する。進捗地図を開いている間だけ、既定45秒間隔で取り直す。

02端末に置くもの

すべて localStorage。IndexedDB は農薬データ(chemdb)だけに使う。

キー中身同期
tankmix:fields圃場マスタ。名前・作物・面積・ポリゴン・重心する
tankmix:works作業。日付×圃場に1件。予定薬液量・薬剤・実績する
tankmix:chemmaster薬剤マスタ。IDは正規化した薬剤名する
tankmix:tombs墓標。削除したIDと時刻。上限500件する
tankmix:pullatどこまで受け取ったか(サーバー時刻)—
tankmix:progresssnap進捗地図の最後の取得結果—
tankmix:deviceid端末の識別子。初回に生成—
tankmix:teamcodeチームコード。大文字小文字を区別—
tankmix:gasurl ほか設定(GAS URL・APIキー・単位・タンク容量)—

レコードは3つの時刻を持つ。この3つの関係が同期の全部といっていい。

  • updatedAt — 端末が中身を変えた時刻。端末の時計
  • pushedAt — 送信に成功した時点の updatedAt
  • 「更新日時」— サーバーが行を書いた時刻。差分取得の物差し

updatedAt > pushedAt なら未送信。これを拾うのが pendingOf(list)。端末の時計と物差しを分けてあるので、圏外で溜めた古い updatedAt のレコードもちゃんと差分に乗る。

03IDの決まり方

作業IDだけ、内容から計算する。二重登録を消すための設計。

2台が圏外で同じ日の同じ圃場を登録すると、以前は別IDになって同期後に2件並んだ。v8.73 から作業IDを「日付＋圃場ID」のハッシュにしてある。両方の端末が同じIDを出すので、サーバーで自然に1件へ収束する。

既知の穴 — nth は端末ローカル

2回目以降(同じ日・同じ圃場をもう一度入れる)の nth は、その端末が持っている作業だけを見て決めている。未同期の2台が両方「2回目」を入れるとどちらも nth=2 になり、別の作業なのにIDが衝突する。1回目が収束するのは設計どおりだが、2回目以降は決定論になっていない。未修正。

種類IDの作り方再利用
圃場newId()(Date.now系・単調増加)されない
作業workIdFor(日付, 圃場ID, nth)される
薬剤正規化した薬剤名される

右の列が肝で、IDが再利用される種類は「削除→作り直し」で同じIDに戻る。受信側で日時を比べずに削除を適用すると、古い墓標が新しいレコードを消す。実際にその不具合があった(08節)。

04差分同期

全件ではなく、変わったレコードだけを送る。送る順と受け取る順に意味がある。

図3 — 1回の同期(送ってから受け取る)
sequenceDiagram
  participant A as 端末A
  participant G as Apps Script
  participant S as シート
  participant B as 端末B

  Note over A: pendingOf(works)
  A->>G: pushWorks { team, items(最大300) }
  G->>S: 30日超の削除済み行を捨てる
  G->>S: 行数を確保 ensureRows_
  Note over G,S: 鍵は チーム＋ID
  G->>S: setValues(全行)
  G-->>A: ok, added, updated, purged, serverTime
  Note over A: 送れた分だけ pushedAt を進める
  Note over A: 墓標は送ったIDだけ引く

  Note over B: since = tankmix:pullat
  B->>G: pull { team, since }
  G->>S: 更新日時が since より後の行だけ
  G-->>B: fields, works, chems, serverTime
  Note over B: 送信状態と実績メモは上書きしない
  Note over B: pullat = serverTime

順番は必ず「送ってから受け取る」。逆にすると、手元の未送信の変更が受信データに埋もれる。共有をオフからオンに戻したときの経路だけこの順が守られておらず、await していない。未修正。

pullat はチームに紐付いていない。チームコードを変えたら捨てる(v8.78)。残すと、新しいチームに前からあるデータが since で弾かれて一生届かない。

05削除の伝わり方

行は消さない。「削除」列を立てて墓標として残し、30日で捨てる。

図4 — 削除の一生
stateDiagram-v2
  [*] --> 端末にある
  端末にある --> 墓標: 外す / addTomb
  墓標 --> 送信中: pushProgress
  送信中 --> 墓標: 失敗(圏外) 墓標は残す
  送信中 --> 送信済: 成功 送ったIDだけ引く
  送信済 --> シートで削除済: 削除列 = 1
  シートで削除済 --> 他端末へ: pull で配る
  シートで削除済 --> [*]: 30日経過 行ごと捨てる
端末から消えた作業は、アプリから触れない

墓標を失うと(送信中に全消ししていた不具合など)、シートの行は生きたまま残り、removeWork はもう届かない。進捗地図が赤いまま永久に戻らない。

v8.80 で progressItems_ が作業IDを返すようにし、進捗地図に「この端末にない作業が n件」と「サーバーから外す」を足した。それまで、残骸を片付ける道がどこにもなかった。

06進捗地図の色

実施済　未実施　対象外

色はサーバーのスナップショットと手元の作業を重ねて決める。同じ圃場に複数の作業がぶら下がることがある(午前と午後で分けた等)ので、「いちばん進んでいる状態」を採る。

既知の穴 — 「大きい方を採る」が、未実施を隠す

put は RANK[新] > RANK[現] のときだけ上書きする。同じ圃場に同じ日の作業が2件あると、片方が done ならもう片方が未実施でも地図は緑になる。

実測で再現(v8.82)。実績を入れた圃場を「＋「〇〇」の○圃場をまとめて追加」でもう一度入れると、addWorks の重複除外が !w.reported なので通ってしまい、workIdFor(date, fieldId, 2) の2件目ができる。このとき作業リストは「1 / 2 済」「あと 1 圃場」と正しく出すが、ポリゴンの fill は #2E7D4F(実施済)のままだった。赤が消えない不具合と逆向きで、こちらは警告帯も出ない。

散布済のチェックを外したときも同じ理屈で、サーバーの done が勝ち続ける。次の自動取得(既定45秒)まで緑のままで、圏外なら戻らない。いずれも未修正。

07シートの構成

スプレッドシート1枚に5シート。行の鍵は「チームコード＋ID」。

シート列数役割鍵
作業24予定と実績。進捗地図の元チーム＋作業ID
圃場マスタ14名前・作物・面積・ポリゴンチーム＋圃場ID
薬剤マスタ11薬剤名・剤型・希釈倍率チーム＋薬剤名
防除記録—確定した台帳。追記のみ記録IDのみ
_共有データ4上書き前の値を残す履歴。200行で打ち切り—

防除記録シートだけチームコード列がなく、記録IDだけで行を探す。作業IDが内容から決まるようになったので、別チームが同じ日に同じ圃場を入れると理屈の上では衝突する。未修正。

日付が化ける

スプレッドシートは "2026-08-27" をセルに入れた時点で Date と解釈する。読み戻すと Date オブジェクトになり、テキスト書式の列へ書き戻すと "Mon Jul 13 2026 00:00:00 GMT+0900" になる。WORK_TEXT_COLS で書式を固定しつつ、ymd_() が Date・ISO文字列・化けた文字列のどれでも yyyy-MM-dd に戻す。

08詰まる所

実際に起きた失敗。設計意図より、こちらのほうが引き継ぐ人の役に立つ。

シートの行数上限で、送信が丸ごと落ちる

v8.80 で修正 / 実データ 999行 : 上限1000行 で発生

機構
シートは新規作成時1000行。getRange でその外を掴むと Those rows are out of bounds で例外になり、その送信が丸ごと落ちる。
波及
pushProgress は「新しい作業＋削除の墓標」を1回で送る。満杯になると削除まで道連れで失敗する。
症状
進捗地図の未実施が何度直しても消えない。アプリ側をいくら直しても届いていなかった。
見逃した
理由
テストの張りぼて(FakeSheet)が黙って行を伸ばしていた。実物と同じ上限を持たせて、初めて再現できた。
対処
ensureRows_() で setValues の前に必ず伸ばす。削除済みの行は30日で捨てる(実データは999行中354行が空の墓標だった)。

墓標を全消しして、削除が永久に伝わらない

v8.78 で修正

機構
送信前に読んだ墓標を送り、成功後に t.works = [] と全消ししていた。await をまたぐ read-modify-write。
症状
送信中(数秒)に外した圃場の削除が一緒に捨てられ、他端末に残り続ける。手元からは消えているので再送のきっかけもない。
対処
送ったIDだけを引く。すぐ上の pendingOf 側は done マップで正しく書けていたのに、墓標だけ配慮が抜けていた。

古い墓標が、入れ直した作業を消す

v8.78 で修正

機構
受信マージの更新の枝には old.updatedAt > inc.updatedAt の比較があるのに、削除の枝にはなかった。
症状
作業IDと薬剤IDは内容から決まる、つまり再利用される。外して入れ直すと同じIDになり、古い削除が追いかけてきて消す。

固形剤の量が、画面と転記で単位が食い違う

v8.78 で修正 / 現場で用量を誤りうる

機構
計算は ml = 総量 ÷ 希釈倍数 の1本で剤型を見ていない(1 mL = 1 g)。単位の判定関数はアグリノート転記の1か所でしか呼ばれず、画面側4か所は " mL" の直書きだった。
症状
水和剤が画面「100 mL」・転記「0.1 kg」。数値は同じだが、粉を体積で量ると用量を外す。
対処
固形剤は「g」で表示。4か所目は <small> タグで書かれていて grep から漏れ、ブラウザで表示させて気づいた。

チームコードを変えても、前のチームのデータが残る

v8.78 で一部対処(消さずに警告)

機構
setTeamCode は localStorage のコードを書くだけ。圃場・作業・薬剤はそのまま残る。
症状
残るだけなら害はないが、そのあと編集すると自動送信で新チームへ流れる。
方針
勝手に消さない。設定タブに警告を出して、判断は使う人に渡す。

useEffect の依存漏れで、地図が白いまま

v8.40 と v8.75 で2度発生

機構
地図を作る effect の依存が []。最初の1回で読み込みに失敗すると二度と走らない。
症状
「圃場タブを一度開かないと進捗地図が出ない」。地図タブ側のリトライで window.google が入り、戻ったとき作り直されて初めて映っていた。
対処
loadAttempt を依存に入れてやり直す。同じ形を v8.40 で一度直していた。履歴を確認せず v8.62 で別の原因(ResizeObserver)と誤診している。

09テスト

ブラウザも Google も要らない。node だけで両方走る。

ファイルやること件数
tools/selftest.cjsapp.js のトップレベル関数を取り出して呼ぶ。ソースの形も検査する155
tools/gastest.cjsCode.gs を張りぼての上で動かし、シートに何を書いたかを見る100
tools/gasharness.cjsSpreadsheetApp の張りぼて。vm で Code.gs を評価する—
tools/fakegas.cjsローカルの受信口。2オリジンで2端末を再現できる—

app.js は ReactDOM.createRoot(...) の行を差し替えて評価し、トップレベルの関数を globalThis へ吐き出す。UIを動かさずに計算だけ試せる。

張りぼては実物の嫌なところを模すのが仕事。"2026-08-27" を Date に化かす、1000行で例外にする、deleteRows で行数が減る。ここを手加減すると、08節のような不具合がすり抜ける。

直したことの確かめ方

テストを足したら必ず対照を取る。修正を戻して、足したテストが実際に落ちることを見る。落ちないテストは何も守っていない。戻したあとはハッシュで元通りを確認する。

GAS は「新規デプロイ」にしない

新規デプロイにすると URL が変わり、全端末の設定を直すことになる。必ず既存デプロイの「編集」から バージョン「新バージョン」で更新する。

APP_VERSION(app.js)と CACHE_VERSION(sw.js)は必ず一緒に上げる。ずれていると selftest が落ちる。
