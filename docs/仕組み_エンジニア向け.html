02端末に置くもの

すべて localStorage。IndexedDB は農薬データ(chemdb)だけに使う。

キー中身同期
tankmix:fields圃場マスタ。名前・作物・面積・ポリゴン・重心する
tankmix:works作業。日付×圃場に1件。予定薬液量・薬剤・実績する
tankmix:chemmaster薬剤マスタ。IDは正規化した薬剤名する
tankmix:tombs墓標。削除したIDと時刻。上限500件する
tankmix:pullatどこまで受け取ったか(サーバー時刻)—
tankmix:progresssnap進捗地図の最後の取得結果—
tankmix:deviceid端末の識別子。初回に生成—
tankmix:teamcodeチームコード。大文字小文字を区別—
tankmix:gasurl ほか設定(GAS URL・APIキー・単位・タンク容量)—

レコードは3つの時刻を持つ。この3つの関係が同期の全部といっていい。

  • updatedAt — 端末が中身を変えた時刻。端末の時計
  • pushedAt — 送信に成功した時点の updatedAt
  • 「更新日時」— サーバーが行を書いた時刻。差分取得の物差し

updatedAt > pushedAt なら未送信。これを拾うのが pendingOf(list)。端末の時計と物差しを分けてあるので、圏外で溜めた古い updatedAt のレコードもちゃんと差分に乗る。

03IDの決まり方

作業IDだけ、内容から計算する。二重登録を消すための設計。

実測で再現してから直した。実績を入れた圃場を「＋「〇〇」の○圃場をまとめて追加」でもう一度入れると、addWorks の重複除外が !w.reported なので通ってしまい、workIdFor(date, fieldId, 2) の2件目ができる。このとき作業リストは「1 / 2 済」と正しく出すのに、ポリゴンの fill は #2E7D4F(実施済)のままだった。

v8.83 の形。まず作業IDで byWork に重ね(スナップショット→手元の順。手元が勝つ)、そのあと圃場ごとに畳んで doneCount === total のときだけ done。1件でも未実施が残れば赤。吹き出しに この日の作業 2件（1件済） を出し、「✓ 散布済にする」は swList.find(w => !w.reported) で未実施側を拾う。

散布済のチェックを外したときにサーバーの done が勝ち続けていたのも、同じ仕組みで直った。作業IDで重ねるときに手元が上書きするため、外した瞬間に赤へ戻る(実測で確認)。

残っている制約。古い Code.gs は進捗に作業IDを返さないので重ねられず、手元だけ済んでいる途中の状態で二重に数える。出るのは赤で、安全側に倒れる。

進行中 — progress をやめて pull に寄せる(v9.03 で照合を開始)

今の形。進捗地図を開いている間、端末は同じ間隔で2回サーバーを呼んでいる——autoPullShared(pull)と refresh(progress)。どちらも pullSec の間隔で走る。

気づいたこと。progress が返す項目は、pull が返す作業(workObj_)にすべて含まれている。id / fieldId / workDate / status / sprayedL / by はそのまま、areaA は reportAreaA、at は reportedAt、atTime は reportedAtTime。しかも地図はもともと pull 由来の p.works を上に重ねている(手元が勝つ)。つまり progress は要らないはず。

「はず」で外さない。v9.03 では、地図の見た目は従来どおり(progress が土台)にしたまま、裏で「受信した作業だけ」で同じ地図を組み、違いがあれば記録する。設定タブ→アプリの更新に「照合 N 回 / 差分 M 回」と出る。progressEntries(items, works, from, to, recorder) の第1引数を空にすれば works だけの結果になる、という形にしてある。

外すときにやること。差分 0 のまま何日か使えたら、(1) fetchProgress と refresh を pullSharedSync に置き換える (2) snap と tankmix:progresssnap を捨てる (3) Code.gs の progress と progressItems_ を消す (4) この照合の仕組みと progressDiffLine ごと消す。片づけまでやって完了。照合だけ残すと、要らない計算が毎回走り続ける。

照合が実データで1件拾った(v9.08 で修正)。「照合6回 / 差分2回」。中身は prevDate 進捗=2026-08-29 / 受信=空 が9圃場。原因はサーバー由来の進捗にだけ日付の範囲を掛けていなかったこと。items は端末に保存した写し(tankmix:progresssnap)から来ることがあり、写しは前に取ったときの範囲のまま。範囲を狭めたあと(v9.01 で 3日 → 2日)や作業日を切り替えた直後は、範囲の外の日が混ざる。手元の作業だけ範囲で切っていたので、写しにしか無い古い日が「前の日に済んだ(青)」として地図に残っていた。直したのは進捗地図そのものの振る舞いで、照合はそれを見つける役に立った——外すための下ごしらえが、外す前に不具合を1つ返した。

効き目の見込み(未実測)。地図を開いている間のサーバー呼び出しが半分になる。progress は1日ぶんで 4,274セル読み(v8.98 の実測)、pull は変化なしで 17,024セル読み。pull のほうが1回は重いので、合計が減るかは実データで測ってから書くこと。減らないなら、外す理由は「経路がひとつになる」ことだけになる。

台帳(防除記録)は作業シートから作り直せる — 進行中(v9.04 で照合を開始)

今の形。端末は同じ散布を2か所へ別々に送っている。pushWorks で「作業」シートへ、record / report / unreport で「防除記録」シートへ。別々に書いているので食い違いうる。

調べた結果。「防除記録」の16列はすべて「作業」にもある。受信日時→更新日時 / 記録ID→作業ID / 散布日→作業日 / 記録者→記録者 / 圃場→圃場名 / 作物→作物 / 面積→実績面積a か 面積a / 薬剤数→薬剤数 / 薬剤内容→薬剤内容 / 総量→総量L / 水量→水量mL÷1000 / 実散布量→実績L / 状態→状態(done なら散布済) / 報告日→実績入力日時 / 備考→実績メモ か 備考 / チームコード→チームコード。記録IDと作業IDは同じもの(どちらもアプリが日付＋圃場IDから決める)。

1つだけ足りなかった。「実績メモ」の列が作業シートに無かった。itemToWork が必ず空を入れていたのはこのため。v9.04 で列24として末尾に足した。

切り替える前に照合する。ledgerRowFromWork_() が作業行から台帳行を作り、ledgerCheck(読み取りのみ)が今の台帳と突き合わせて 一致 / 食い違い / 台帳に無い / 作業に無い の件数と、違った列を返す。設定タブ→送信・共有の「🧾 台帳の照合(開発用)」から呼ぶ。シートは書き換えない。2枚とも丸ごと読むので自動では呼ばない。

照合で実際に食い違いが1つ見つかった。unreport は実散布量と報告日は消すが、備考に入れた実績メモは消さない。そのため実績を取り消しても台帳には実績メモが残る。作業シートから作り直すと予定のメモになる。unreport の送りものは {id} だけで予定のメモを知らないので、台帳側だけでは直せない(消すことしかできない)。この食い違いは提案Dを通せば無くなるので直さず、テストで固めてある(gastest 20番)。

実データで照合した結果(2026-08-31)。一致 92 / 食い違い 83 / 台帳に無い 258 / 作業に無い 113。食い違いの内訳は 記録者 75 / 状態 6 / 面積 2。

食い違いの原因は3つとも「台帳を別経路で送っていること」

記録者 75件。台帳の記録者は data.recorder(= localStorage["tankmix:recorder"]、送信した端末の名前)、作業シートの記録者は w.by(実施済を押した人)。別のものを書いている。v8.99 で「端末ごとに作業者名が違う」を直したとき、作業シート側だけ直して台帳側を直していなかった。

台帳に無い 258件・状態 6件。作業シートは変更のたびに自動で送られるが、台帳は syncPending で送られ、しかも「いま選んでいる作業日」の未送信だけが対象(w.workDate === workDate)。さらに他の端末から受け取った作業は synced:true / reportSynced:true になる(意図的。「台帳へ送るのは、その作業をした端末の役目」)。元の端末が送らなかった台帳の行は、誰も送らない。

読み違えた点。最初、「台帳に無い作業がすべて『薬剤なし』」を手がかりだと書いたが、作業シートは生存542行すべてが薬剤なし(薬剤JSON 全行空・総量L・水量mL 0行)だった。あの内訳は何も語っていなかった。実データを見るまで分からなかった。

作り直し(v9.07)。ledgerRebuild。作業シートを元に台帳の行を足す・直す。行は消さない——台帳にしか無い113件(古い版で入れた記録・作業シートから消えた作業)はそのまま残す。受信日時も書き換えない(ledgerNorm_ が両方 "" にするので比較で必ず弾かれる)。削除済みの作業は足さない。チームが違う行は触らない。

元帳なので、いきなり書かない。dryRun で「足す/直す/そのまま/触らない」の件数と直る列を先に返す。下見を取っていなければ実行ボタンが出ないし、実行前に件数入りの確認を出す。下見が1セルも書いていないことは、ハーネスに書き込みセル数の数取り(_writeCells)を足して機械で確かめている——「書かないつもり」では足りない。

行の確保を忘れない。実データでは 254 行足す見込み。ensureRows_ を呼ばずにシートの行数を超えて書くと例外になり、作り直しが途中で止まる。

次にやること。作り直したあと ledgerCheck が食い違い 0 を出すのを確かめてから、(1) pushWorks のあとに、いま押し込んだ作業ぶんだけ台帳を更新する (2) syncPending の台帳送信をやめる (3) applyRecord_ / pushRecords / buildRow_ / findRow_ / claimRow_ と record / report / unreport を消す。(1) を先にやること。順番を逆にすると、その間の実績が台帳に残らない。

日付が化ける

スプレッドシートは "2026-08-27" をセルに入れた時点で Date と解釈する。読み戻すと Date オブジェクトになり、テキスト書式の列へ書き戻すと "Mon Jul 13 2026 00:00:00 GMT+0900" になる。WORK_TEXT_COLS で書式を固定しつつ、ymd_() が Date・ISO文字列・化けた文字列のどれでも yyyy-MM-dd に戻す。

片方だけ期間で絞り、手元にある作業を「残骸」と呼ぶ

v9.10 で修正

機構
進捗地図の「サーバーにだけ残っている作業」は、手元だけを取得範囲(直近3日)で絞り、サーバー側の写しは絞っていなかった。写し(tankmix:progresssnap)は端末に残るので、作業日を切り替えた直後は前の期間のまま。手元が新しい範囲、写しが古い範囲になり、突き合わせが噛み合わない。
症状
前の期間の作業が丸ごと「⚠ この端末にない作業がN件、サーバーに残っています」に出る。手元にちゃんとある作業なのに残骸として並ぶ。圏外だと取り直しが終わらないので、その状態が続く。
なぜ重いか
「🧹 サーバーから外す」は墓標を積んで送る。他の端末からも消え、取り消せない。確認文は「直近3日の作業N件」と言うが、実際に消えるのは別の期間の作業。
対処
サーバー側の写しにも同じ範囲を掛ける。日付が入っていない行は判断できないので拾わない側に倒す(消すのは戻せない)。useMemo に直書きしていた計算を serverOrphans に出し、9件の検査を付けた。
同じ形
v9.08 で progressEntries に入れたのと同じ欠陥。あのとき「サーバー由来にも範囲を掛ける」と直したが、同じ写しを使う隣の計算を見ていなかった。片方を直したら、同じ入力を使う場所を数え上げること。

Leaflet に入れた手当てが、Google 側に入っていない

v9.10 で修正・未検証

機構
進捗地図は Leaflet と Google の2実装。Leaflet 側は「地図の高さが入ってから寄せる」を持つが、Google 側は高さを見ずに寄せ、寄せた印(fittedRef)まで立てていた。
症状
高さが 0 のうちに fitBounds が走ると倍率がでたらめになる。しかも印が立つので、下の ResizeObserver の「大きさが決まったらもう一度寄せる」も走らない。直る機会が無い。
対処
Google 側にも高さの条件を入れる。Google 版は API キーが無く未検証なので、直したのは並びが揃っていることまで。selftest で両方の並びを固定した。
教訓
同じ画面を2つの実装で持つと、片方だけ直した手当てが残る。PROGRESS_LABEL_MIN_ZOOM のように共通の定数へ出せるものは出す。出せない手当ては、テストで並びを揃えて固定する。

張りぼては実物の嫌なところを模すのが仕事。"2026-08-27" を Date に化かす、ISO の日時も同じく化かす、setNumberFormat("@") を当てた列だけは化かさない、1000行で例外にする、deleteRows で行数が減る。ここを手加減すると、08節のような不具合がすり抜ける。
