01全体像

app.js は React.createElement に展開済みのプレーンJS。ブラウザがそのまま読む。

端末はそれぞれが完全な記録を持つ。サーバーは同期の待ち合わせ場所であって、正本ではない。圏外で1日中作業しても、端末だけで予定・計算・実績入力が完結する。

常時接続は持たない

WebSocket も常駐ポーリングもない。送るときだけ HTTPS で1往復する。アプリを閉じている間は同期が動かないだけで、次に開けば未送信ぶんから再開する。進捗地図を開いている間だけ、既定45秒間隔で取り直す。

02端末に置くもの

すべて localStorage。IndexedDB は農薬データ(chemdb)だけに使う。

キー中身同期
tankmix:fields圃場マスタ。名前・作物・面積・ポリゴン・重心する
tankmix:works作業。日付×圃場に1件。予定薬液量・薬剤・実績する
tankmix:chemmaster薬剤マスタ。IDは正規化した薬剤名する
tankmix:tombs墓標。削除したIDと時刻。上限500件する
tankmix:pullatどこまで受け取ったか(サーバー時刻)—
tankmix:progresssnap進捗地図の最後の取得結果—
tankmix:deviceid端末の識別子。初回に生成—
tankmix:teamcodeチームコード。大文字小文字を区別—
tankmix:gasurl ほか設定(GAS URL・APIキー・単位・タンク容量)—

レコードは3つの時刻を持つ。この3つの関係が同期の全部といっていい。

  • updatedAt — 端末が中身を変えた時刻。端末の時計
  • pushedAt — 送信に成功した時点の updatedAt
  • 「更新日時」— サーバーが行を書いた時刻。差分取得の物差し

updatedAt > pushedAt なら未送信。これを拾うのが pendingOf(list)。端末の時計と物差しを分けてあるので、圏外で溜めた古い updatedAt のレコードもちゃんと差分に乗る。

03IDの決まり方

作業IDだけ、内容から計算する。二重登録を消すための設計。

2台が圏外で同じ日の同じ圃場を登録すると、以前は別IDになって同期後に2件並んだ。v8.73 から作業IDを「日付＋圃場ID」のハッシュにしてある。両方の端末が同じIDを出すので、サーバーで自然に1件へ収束する。

2回目以降は端末で分ける(v8.86)

nth はその端末が持っている作業だけを見て決めるので、未同期の2台が両方「2回目」を入れるとどちらも nth=2 になり、別の作業なのにIDが衝突していた。nth が2以上のときだけ端末IDを混ぜる。1回目は混ぜない — ここが端末をまたいで一致するのは設計意図で、混ぜると合流しなくなり進捗地図に同じ圃場が二重に出る。2回目以降は「午前と午後で分けた」のようなその端末の都合なので、別端末のそれと同じものだと見なす根拠がない。

既存データは作り直していない。IDは作業に保存されていて、workIdFor の呼び出しは makeWork の1か所だけ。過去の作業も台帳の行もそのまま結び付く。

種類IDの作り方再利用
圃場newId()(Date.now系・単調増加)されない
作業workIdFor(日付, 圃場ID, nth, 端末ID)
端末IDは nth≥2 のときだけ効く		される
薬剤正規化した薬剤名される

右の列が肝で、IDが再利用される種類は「削除→作り直し」で同じIDに戻る。受信側で日時を比べずに削除を適用すると、古い墓標が新しいレコードを消す。実際にその不具合があった(08節)。

順番は必ず「送ってから受け取る」。逆にすると、手元の未送信の変更が受信データに埋もれる。共有をオフからオンに戻したときの経路だけこの順が守られていなかった。v8.87 で修正(08節)。

serverTime は今より2分手前を返す(PULL_LAG_MS)。押し込み中の行を取りこぼさないための幅で、代わりに直近2分の行は毎回配り直される(08節)。

pullat はチームに紐付いていない。チームコードを変えたら捨てる(v8.78)。残すと、新しいチームに前からあるデータが since で弾かれて一生届かない。

墓標を失うと(送信中に全消ししていた不具合など)、シートの行は生きたまま残り、removeWork はもう届かない。進捗地図が赤いまま永久に戻らない。

v8.80 で progressItems_ が作業IDを返すようにし、進捗地図に「この端末にない作業が n件」と「サーバーから外す」を足した。それまで、残骸を片付ける道がどこにもなかった。

直した穴 — 圃場単位ではなく作業単位で数える(v8.83)

v8.82までの実装。put は RANK[新] > RANK[現] のときだけ上書きしていた。同じ圃場に同じ日の作業が2件あると、片方が done ならもう片方が未実施でも地図は緑になった。

実測で再現してから直した。実績を入れた圃場を「＋「〇〇」の○圃場をまとめて追加」でもう一度入れると、addWorks の重複除外が !w.reported なので通ってしまい、workIdFor(date, fieldId, 2) の2件目ができる。このとき作業リストは「1 / 2 済」と正しく出すのに、ポリゴンの fill は #2E7D4F(実施済)のままだった。

v8.83 の形。まず作業IDで byWork に重ね(スナップショット→手元の順。手元が勝つ)、そのあと圃場ごとに畳んで doneCount === total のときだけ done。1件でも未実施が残れば赤。吹き出しに この日の作業 2件（1件済） を出し、「✓ 散布済にする」は swList.find(w => !w.reported) で未実施側を拾う。

散布済のチェックを外したときにサーバーの done が勝ち続けていたのも、同じ仕組みで直った。作業IDで重ねるときに手元が上書きするため、外した瞬間に赤へ戻る(実測で確認)。

残っている制約。古い Code.gs は進捗に作業IDを返さないので重ねられず、手元だけ済んでいる途中の状態で二重に数える。出るのは赤で、安全側に倒れる。

防除記録シートだけチームコード列がなく、記録IDだけで行を探していた。作業IDが内容から決まるので、別チームが同じ日に同じ圃場を入れると衝突する。v8.85 で修正(08節)。チームコードは列16、つまり末尾に足してある。先頭に挿すと既存シートの全列がずれ、設置済みのスプレッドシートを手で直すことになるため。他のシートは列1なので、位置は揃っていない。

日付が化ける

スプレッドシートは "2026-08-27" をセルに入れた時点で Date と解釈する。読み戻すと Date オブジェクトになり、テキスト書式の列へ書き戻すと "Mon Jul 13 2026 00:00:00 GMT+0900" になる。WORK_TEXT_COLS で書式を固定しつつ、ymd_() が Date・ISO文字列・化けた文字列のどれでも yyyy-MM-dd に戻す。

08詰まる所

実際に起きた失敗。設計意図より、こちらのほうが引き継ぐ人の役に立つ。

45秒ごとに、変わっていないものまで作り直していた

v8.91 で差分描画に / 実測あり

機構
描画の effect は p.statusByField に依存している。これは取得のたびに別の Map になるので、中身が1つも変わっていなくても effect が走り、clearLayers() して全部作り直していた。札があると 200圃場で 173.7ms(すぐ上)。
対処
圃場1枚を描くのに要る材料を1本の文字列にまとめ(fieldDrawSig)、前回と違うものだけ消して作り直す(diffDraw)。部分的に塗り替えるような細工はしない。1枚を作り直すのは安く、そこを間違えると「色だけ古いまま」という直しにくい不具合になる。
実測
node での中央値。変化なしのとき 50圃場 0.17ms、100圃場 0.14ms、200圃場 0.40ms、400圃場 0.74ms(いずれも作り直し0枚)。1枚だけ変わったときは 0.11〜0.47ms で、触るのはその1枚だけ。200圃場で 173.7ms → 0.40ms。
危ないところ
署名に入れ忘れたものは「サーバーには届いているのに地図が変わらない」という形で出る。利用者からは共有が壊れたのと見分けが付かず、原因を探す場所を間違える。実績・記録者・入力日・報告面積・未送信の印は色を変えないが、圃場をタップした吹き出しに出るので署名に入れてある(落とすと吹き出しだけ古くなる)。検査を21件足し、落とすと落ちることを確かめた。
もう一つの
落とし穴
地図を作り直したとき(loadAttempt でのやり直し・エンジン切替)に描いたという記憶を捨てること。残すと差分が「もう描いてある」と判断し、新しい地図が空のままになる。作った直後と後片付けの両方で捨てている。

全画面の操作ボタンが、実機でだけ押せない場所に回る

v8.90 で修正 / エミュレータでは再現しなかった

機構
v8.89 は右上に position:fixed で縦積みし、上端を env(safe-area-inset-top) から測っていた。実機(iPhone)では覆い(mapWrapFull, zIndex 900)が見出しとタブバーを隠しきれず、上の2つが見出しの裏に回って押せなくなった。
再現できな
かった理由
手元のエミュレータ(Chromium・375x812)では env(safe-area-inset-top) が 0 で、4つとも画面内に収まり vis:true だった。実機の画面写真で初めて分かった。上端は端末ごとの差が大きく、手元で確かめられない。
対処
上端をやめた。作図の全画面で既に使っている下の帯(drawBarFull)と同じ形にする。ノッチも覆いの効き方も関係なくなり、親指も届く。
詰まった
ところ
justify-content: center のままだと、幅が足りないときに左側へはみ出してスクロールでも届かない(375pxで先頭が -27px になった)。safe center にすると、収まらないときだけ先頭寄せに落ちる。
寸法の
決め方
文字と余白はブラウザで実測して詰めた。絵文字の幅は環境で変わるので机上の計算が当てにならない。360px幅に1行で収まるまで縮め、さらに flex-shrink:1 + min-width:0 で「はみ出す前に縮む」安全網を足した。iOSの絵文字はこの実測(Chromium)より広いため。
検証
360x780 / 375x812 / 375x390(横向き) / 768x1024 / 1280x720 の5つで、帯が下端にあり4つとも画面内、ボタンの高さ45pxを確かめた。
続き
これでも直らなかった。iPhone15 では帯そのものが出なくなった(すぐ下)。

fixed が当てにならない端末がある

v8.92 で fixed をやめた / 再現できていない

症状
iPhone15 の全画面で、下の帯(v8.90)がまったく出ない。その前の版(v8.89)では、上端に置いたボタンのうち上の2つが見出しの裏に回っていた。覆い(mapWrapFull, position:fixed; inset:0)自体も見出しとタブバーを隠しきれていない。
調べた
こと
祖先に transform があると fixed の基準が画面でなくなる。これを当てて再現を試みると、覆いが縮む症状(v8.89の画面写真そのもの)は再現できたが、帯が消える症状は再現できなかった(旧方式の帯も覆いの下端に出た)。index.html の .app-shell 側にも transform・filter・contain は無い。原因は未特定。
対処
原因を突き止める代わりに、原因になりうる仕組みそのものをやめた。帯は覆いの子で、覆いは display:flex; flex-direction:column。ならば「一番下の子」として普通に置けばよく、position:fixed も z-index も要らない。レイアウト上の場所を実際に占めるので、画面外や何かの裏へ押し出されようがない。地図(flex:1)がそのぶん縮む。
効果の
確かめ方
祖先に transform を当てて覆いを縮ませた状態(107〜791px)でも、帯は覆いの下端(729〜791px)に付いて回り、4つとも画面内に残った。覆いが画面を覆えなくても帯は出る。
残る
不確かさ
元の症状を再現できていない以上、これで直ったとは言えない。実機で確かめるまでは未解決として扱う。

札が、思っているより2桁高い

v8.89 で逃げ道を用意(消せるようにした) / 実測あり

機構
圃場名・面積の札は、圃場1枚につきDOMを1つ(Leaflet の permanent ツールチップ)ないし2つ(Google は名前と面積で別マーカー)作る。効くのはパンより作り直しで、札は中央寄せのために実寸を測らせるのでレイアウトが同期的に走る。進捗地図は45秒ごとに全部作り直すため、そのたびに画面が止まる。
実測
Leaflet 1.9.4 / PC(Chromium・1280x720)・中央値。作り直し(札なし→札あり)は 50圃場 1.4→28.2ms、100圃場 2.3→74.5ms、200圃場 3.5→173.7ms、400圃場 7.6→537.5ms。1回のパンは 0.5→0.7ms 〜 1.3→1.7ms で、こちらの差は小さい。圃場数に対して加速度的に増える。スマホはこれより数倍遅い。
対処
倍率のしきい値(PROGRESS_LABEL_MIN_ZOOM)だけでは、寄った状態で圃場が密なときに逃げ道がない。labelsVisible(on, zoom) を足して手で消せるようにした。全画面でも切り替えられる。
測り方の
落とし穴
最初の計測は2倍に膨らんでいた。Leaflet は札をフェードさせてから消すので、clearLayers() の直後に数えると前の札がまだDOMに残っている。同期のループで測ると setTimeout が走らず、古い札を抱えたまま最後まで測ることになる。作り直しのあと待ってから測る。これをリークだと誤診しかけた。
残件
45秒ごとの取得で中身が変わっていなくても全部作り直していた(statusByField が毎回別の Map になるため)。v8.91 で差分描画にした(すぐ下)。

共有をオンに戻すと、受け取りが送信を追い越す

v8.87 で修正

機構
オンに戻す効果は autoPushFields → autoPushChems → autoPushWorks → autoPullShared の順に並べてあった。ところが押し込み3つは1.5秒の debounce 付きで、autoPullShared だけ即座に走る。並べた順に関係なく、受け取りが1.5秒先に走る。
症状
オフの間にたまった未送信の変更が、受け取った内容に埋もれたまま送られない。keepLocalEdit と編集日時の比較が効くので消えはしないが、送信のきっかけを失って次の編集まで残る。
対処
syncShared と同じく、下位の同期関数(pushFieldsSync 等)を await で直列に呼ぶ。auto* は使わない。途中で共有をオフに戻されたら alive で打ち切る(オフにしたあとに送信が飛ばないように)。
検証
効果の中身をソースから取り出して、4つの呼び出しの順・await の数・auto* を使っていないことを見ている。UIを動かさずに順序を固定できる。

2台が同時に「2回目」を入れると、片方が消える

v8.86 で修正 / 移行なし

機構
makeWork は空き番号 nth をその端末が持っている作業だけから探す。未同期の2台が同じ日・同じ圃場の2件目を作ると、どちらも nth=2 にたどり着いて同じIDになる。
症状
台帳は「チーム＋ID」で上書きするので、後から送ったほうが相手の2件目を書き換える。独立に作った別の作業なのに片方が黙って消える。
対処
nth が2以上のときだけ端末IDを混ぜる。1件目には混ぜない — 端末をまたいで一致させ1件に合流させるのが v8.73 からの設計意図で、混ぜると進捗地図に同じ圃場が二重に出る。
移行
不要。IDは作業に保存されていて、workIdFor を呼ぶのは makeWork の1か所だけ。作り直すのは新しく作る作業のIDだけで、過去の作業も台帳の行もそのまま結び付く。
残る差
localStorage が使えない端末は起動のたびに端末IDが変わる(d-tmp-)。その端末では2件目のIDが起動をまたいで安定しない。元から degrade している経路なので、これ以上は詰めていない。

受信の基準時刻が、書き込み中の行を追い越す

v8.85 で緩和(上限つき) / 実測はしていない

機構
押し込み(upsertRows_)は行を組み立てる前に更新日時 at を採り、そのあと ensureRows_ と setValues を通ってから実際にシートへ載る。この間に別の端末が pull で基準時刻を採って読み終えると、その行は「at は基準時刻より古いのに、読んだ時点ではまだシートに無い」状態をすり抜ける。
症状
pull した端末は基準時刻を保存して次回そこから先だけを求めるので、その行は永久に配られない。消えたことに気づく手立てがない。
なぜ
重なるか
pull は doRead_ でロックを取る前に抜ける。読みを速くするための設計で、そのぶん押し込みとの重なりが排除されていない。
対処
pull にもロックを取らせる案と迷ったが、他端末の送信を待って busy を返すようになり、電波の悪い現場で新しい失敗モードが増える。代わりに返す基準時刻を PULL_LAG_MS(2分)手前にした。書き込み中だった行は次回もう一度配られる。
代償
直近2分の行を毎回配り直す。マージは冪等なので害はないが、編集日時が進んでいないものまで適用すると保存と再描画が毎回走るので、アプリ側に keepLocalEdit を置いて止めた。
限界
上限つきの保証。at を採ってから setValues が載るまでが2分を超えて長引けば、依然として取りこぼす。この所要時間は実測していない。

更新日時が Date に化けて、since の比較が壊れる

v8.85 で修正 / 圃場マスタ・薬剤マスタのみ

機構
更新日時は ISO 文字列で書くが、書式を固定していない列ではシートが日時として解釈し、読み戻すと Date で返る。String() すると "Wed Aug 26 2026 ..." になり、ISO との辞書順比較が壊れる。作業シートだけ WORK_TEXT_COLS で守られており、圃場マスタと薬剤マスタが抜けていた。掃除の側は対処済みなのに pullRows_ が素通しだった。
症状
"W" > "2" なので常に「新しい」と判定される。取りこぼしではなく配り過ぎで、害は軽いが since の絞り込みがその行だけ効かなくなる。
対処
atIso_() を切り出して読み側で吸収し、FIELD_TEXT_COLS / CHEM_TEXT_COLS でそもそも化けさせないようにした。両方やる。
見逃した
理由
張りぼてが ISO の日時を化かしておらず、setNumberFormat も素通りだった。さらに Date の realm が違い、Code.gs 側の instanceof Date が常に falseだった(09節)。

別チームが、同じ記録IDで台帳の行を奪い合う

v8.85 で修正 / 台帳(防除記録シート)だけ取り残されていた

機構
findRow_ が記録IDだけで行を探していた。記録IDは作業IDそのもので、v8.73 から「日付＋圃場ID」で決まる。つまりチームが違っても同じIDになる。圃場マスタ・作業シートは upsertRows_ が「チーム＋ID」で分けていたのに、台帳だけチームコード列を持っていなかった。
症状
別チームが同じ日に同じ圃場を入れると、後から送ったほうが相手の行を書き換える。report なら相手の記録が勝手に「散布済」になり、実散布量と報告日まで相手のものに置き換わる。テストで再現させた。
対処
列16に「チームコード」を足し、findRow_ を「記録ID＋チーム」で探すようにした。末尾に足しているのは、先頭に挿すと既存シートの全列がずれ、設置済みのスプレッドシートを手で直すことになるため。
移行
v8.84 以前に書かれた行はチーム欄が空で、どのチームのものか判別できない。拾えないと report が既存行を見つけられず二重行になるので、第2段として拾い、拾った側が claimRow_ でチームを書き戻す。触るたびに1行ずつ移行される。別チームが同じ記録IDを持っていた場合は先に触ったほうがその行を取るが、これは v8.84 までと同じ挙動で、情報が無い以上これ以上は詰められない。
互換
team を送らない旧アプリからはIDだけで探す。旧アプリ × 新GAS を壊さないため。

保存に失敗しても、何も起きない

v8.84 で修正 / 実測では Chromium の上限は約50MB、iOS Safari は一般に5MB

機構
save() は catch で console.error するだけだった。React の状態は先に更新されているので、画面には入ったように見える。
症状
その日の実績を入れ、作業を終え、アプリを開き直して初めて消えているのに気づく。静かなデータ消失。
確率
作業1,503件＋圃場3枚で 575KB(1件約380バイト)。実データ規模では余裕があるが、圃場の頂点が多い使い方ではいつか届く。
対処
saveFailHook をトップレベルに置き、App が起動時に差し込む。失敗したら自分で閉じるまで消えない赤帯を出す。トーストだと見逃す。
検証
Storage.prototype.setItem を QuotaExceededError で落ちるように差し替え、帯が出て localStorage に入っていないことを確認した。code 22 / 1014 も見る。

シートの行数上限で、送信が丸ごと落ちる

v8.80 で修正 / 実データ 999行 : 上限1000行 で発生

機構
シートは新規作成時1000行。getRange でその外を掴むと Those rows are out of bounds で例外になり、その送信が丸ごと落ちる。
波及
pushProgress は「新しい作業＋削除の墓標」を1回で送る。満杯になると削除まで道連れで失敗する。
症状
進捗地図の未実施が何度直しても消えない。アプリ側をいくら直しても届いていなかった。
見逃した
理由
テストの張りぼて(FakeSheet)が黙って行を伸ばしていた。実物と同じ上限を持たせて、初めて再現できた。
対処

固形剤の量が、画面と転記で単位が食い違う

09テスト

ブラウザも Google も要らない。node だけで両方走る。

ファイルやること件数

tools/gastest.cjsCode.gs を張りぼての上で動かし、シートに何を書いたかを見る127
tools/gasharness.cjsSpreadsheetApp の張りぼて。vm で Code.gs を評価する—

app.js は ReactDOM.createRoot(...) の行を差し替えて評価し、トップレベルの関数を globalThis へ吐き出す。UIを動かさずに計算だけ試せる。

張りぼては実物の嫌なところを模すのが仕事。"2026-08-27" を Date に化かす、ISO の日時も同じく化かす、setNumberFormat("@") を当てた列だけは化かさない、1000行で例外にする、deleteRows で行数が減る。ここを手加減すると、08節のような不具合がすり抜ける。

張りぼての Date はvm の外で作られる。そのまま渡すと Code.gs 側の v instanceof Date が realm 違いで必ず false になり、ymd_・atIso_・掃除の Date 分岐が一度も通らないままテストが通っていた(文字列パースのフォールバックが拾っていた)。makeContext でこちら側の Date を渡して realm を揃えている。

直したことの確かめ方

テストを足したら必ず対照を取る。修正を戻して、足したテストが実際に落ちることを見る。落ちないテストは何も守っていない。戻したあとはハッシュで元通りを確認する。

GAS は「新規デプロイ」にしない
